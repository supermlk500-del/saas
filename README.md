# 织慧通项目说明

## 这是什么

这是一个面向纺织生产场景的系统，项目名称叫 **织慧通**。

它当前主要解决两类问题：

1. **排产**
   - 来料批次进来之后，怎么安排生产
   - 走哪条工艺路线
   - 每道工序安排到哪台设备
   - 计划时间怎么排

2. **质检**
   - 图片离线质检
   - 实时视频流质检
   - 质检结果留档
   - 异常记录和闭环处理

你可以把它理解成一个：

**“胚布排产 + 质检 + 异常闭环”的生产管理系统**

---

## 这个项目现在做到了什么

当前已经落地的核心能力有：

- 来料批次管理
- 工艺路线管理
- 工序模板管理
- 设备与设备能力管理
- 生产计划管理
- 工序计划管理
- 甘特图排产展示
- 图片离线质检
- 实时视频流质检
- 质检结果查看
- 异常闭环处理

当前系统的主业务链路是：

**来料批次 -> 工艺路线 -> 生产计划 -> 工序计划 -> 质检 -> 异常**

## 前后端怎么连起来

前端调用后端时使用代理前缀：

`/prod-api`

也就是说：

- 前端页面请求的是 `/prod-api/...`
- 实际会被代理到 `http://localhost:8080/...`

所以正常开发时你只需要：

1. 启动 MySQL
2. 启动后端
3. 启动前端

然后打开前端地址即可。

## 质量检测是怎么做的

当前系统不是用 Python 单独跑质检服务，而是：

**Java 后端内部直接加载 ONNX 模型完成推理**

当前流程大致如下：

### 图片离线质检

1. 前端上传一张图片
2. Java 后端接收图片
3. Java 调用 ONNX Runtime 推理
4. 生成结果图
5. 写入质检记录和附件记录

### 实时视频流质检

1. 前端打开电脑摄像头
2. 前端和后端建立实时检测会话
3. 前端持续发送视频帧
4. 后端持续推理并返回检测框
5. 前端把检测框叠加到视频预览层
6. 关键帧可单独保存为正式质检记录

## 你可能最容易困惑的几个点

### 1. 为什么有 `python-backend` 目录，但现在又不用它？

因为这个项目中途经历过方案调整。

现在最终采用的是：

**Java 后端 + ONNX Runtime 本地推理**

所以 `python-backend/` 只是历史遗留目录，不是当前主运行方案。

### 2. 这个系统是订单驱动还是批次驱动？

当前核心主链路更偏向：

**来料批次驱动**

也就是说，现在主要是根据来料批次做排产和质检，不是完整订单驱动系统。

订单管理在当前版本中不是最核心的已落地主链路。

### 3. 为什么有些页面看起来比另一些页面更完整？

因为当前版本是按“主业务链路优先”做的。

优先级最高的是：

- 批次
- 工艺
- 排产
- 质检
- 异常

其他外围域（例如订单深度业务）还在后续扩展中。

## 常见问题

### 1. 前端能打开，但没有数据

先检查：

- MySQL 是否启动
- 数据库 `zhihuitong` 是否存在
- 是否已经导入 SQL
- 后端是否正常启动

### 2. 前端页面能打开，但按钮没反应

先检查：

- 后端是不是已经启动在 `8080`
- 前端代理是否正常
- 浏览器控制台有没有报错

### 3. 实时质检打不开摄像头

先检查：

- 浏览器是否允许摄像头权限
- 当前页面是否在允许调用摄像头的环境中
- 是否成功选择摄像头资源

### 4. 质检结果图不显示

先检查：

- `photo/results` 目录里是否真的生成了图片
- 后端是否正确返回了相对路径
- 前端是否能访问这些图片路径

### 5. 模型推理报错

先检查：

- `docs/best.onnx` 是否存在
- Java 后端配置里的模型路径是否正确
- ONNX Runtime 依赖是否正常
