## 1. 项目概述

### 1.1 系统背景

胚布排产质检系统面向纺织生产场景，目标是将来料批次、工艺路线、设备能力、生产计划、工序执行、质量检测和异常处理整合到一个统一平台中。系统既要满足生产管理人员对排产效率的要求，也要满足质检人员对过程质量记录、影像采集和异常追踪的要求。

结合当前项目结构，可以看出本系统不是单一的 CRUD 管理平台，而是围绕以下业务主线展开：

- 来料批次管理
- 工艺路线与工序配置
- 设备能力约束管理
- 生产计划与工序排产
- 工序级质量记录
- 图像/视频质检数据沉淀
- 异常记录与闭环处理
- 追溯分析与看板展示

### 1.2 系统目标

系统建设目标分为业务目标和技术目标两部分。

业务目标：

- 实现来料批次信息规范化录入和跟踪。
- 建立工艺路线、工序和设备能力之间的标准关系。
- 支持生产计划按工序拆分并分配设备与时间窗口。
- 支持离线质检和视频质检两种模式的数据记录。
- 实现质检异常的登记、处理、追踪和结果闭环。
- 支持批次、工序、质检记录的正向与逆向追溯。

技术目标：

- 建立统一的数据结构和接口规范。
- 前后端采用可扩展架构，便于后续接入订单、客户、报表和 AI 辅助排产。
- 形成与当前真实数据库一致的设计文档，降低实现偏差。

### 1.3 技术架构

当前项目采用前后端分离架构：

- 前端：`Vue + TypeScript + Vite + Ant Design Vue + Pinia + Axios`
- 后端：`Spring Boot + MyBatis-Plus + MySQL`
- 数据库：`zhihuitong`
- 前端代理：`/prod-api -> http://localhost:8080`

当前实现现状：

- 前端页面和模块骨架已经较完整，已覆盖来料、工艺、排产、质检、执行、追溯、系统管理等目录。
- 采用 `code + msg + data/rows` 结构。
- 后端当前仍以基础脚手架为主，仅具备启动、健康检查、统一返回、异常处理、跨域配置和占位登录接口。
- 因此本文档中的接口设计是“目标后端接口规范”，并不等同于当前后端已全部实现。

## 2. 数据库设计

### 2.1 数据库概览

本系统真实数据库为 `zhihuitong`。通过真实库文件元数据校验后，确认核心业务表共 14 张。

需要特别说明的事实：

- MySQL 当前实例启用了 `lower_case_table_names=1`
- 因此真实表名为全小写，如 `batchinfo`、`processroute`、`productionplan`
- 字段名保持 camelCase，如 `batchId`、`routeId`、`planStepId`

这意味着开发实现、实体映射、SQL 脚本和文档描述必须统一到真实表名，而不能混用驼峰表名和下划线表名。

### 2.2 数据表清单及说明

### 2.3 数据库关系链概览

- 主链路：`batchinfo -> productionplan -> planstep -> { processparameter, qcrecord, exceptionrecord }`
- 工艺链：`processroute -> routestep -> processstep`
- 设备链：`processstep <-> stepmachinecapability <-> machine`
- 质量链：`qcitem -> qcrecord`，`qccamera -> inspectiondata`，`qcrecord -> inspectiondata`

结构特点：

- 系统围绕“工序级计划”和“工序级质检”展开
- `planstep` 是计划、执行、质检和异常的共同关联点
- 质量模块已经具备与视频检测能力对接的基础数据结构
- 当前数据库仅覆盖排产质检核心域，不覆盖订单、客户、产品、系统管理等外围域

## 4. 接口设计

接口设计原则：

- 文档层统一采用 REST 风格 `/api/**`
- 当前前端已有部分调用使用 `/business/**`，建议后端后续通过兼容路由或网关映射逐步过渡
- 列表接口统一返回：`{ code, msg, rows, total }`
- 明细接口统一返回：`{ code, msg, data }`
- 写操作统一返回：`{ code, msg, data }`
- 分页参数统一：`pageNum`、`pageSize`
- 查询条件统一通过 query string 传递

统一响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

列表响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "rows": [],
  "total": 0
}
```

### 4.1 批次/订单接口

#### GET /api/batches

用途：批次列表查询。

请求参数：

- `pageNum`
- `pageSize`
- `batchNo`
- `supplier`
- `dateFrom`
- `dateTo`

返回字段建议：

- `batchId`
- `batchNo`
- `supplier`
- `inDate`
- `weight`
- `width`
- `composition`
- `status`

#### GET /api/batches/{batchId}

用途：批次详情查询。

返回内容建议包括：

- 批次基础信息
- 关联生产计划摘要
- 关联质检记录摘要
- 异常记录数量

#### POST /api/batches

用途：新增批次。

请求体示例：

```json
{
  "batchNo": "BAT-20260522-001",
  "supplier": "华东供应商A",
  "inDate": "2026-05-22 08:30:00",
  "weight": 2500.50,
  "width": 168.00,
  "composition": "棉 95%, 氨纶 5%",
  "note": "首批试产"
}
```

#### PUT /api/batches/{batchId}

用途：修改批次基础信息。

#### DELETE /api/batches/{batchId}

用途：删除或作废批次。

建议说明：

- 物理删除风险较高
- 实现层建议优先使用逻辑作废字段
- 若暂不改表，可在服务层限制已被计划引用的批次不可删除

#### POST /api/batches/import

用途：CSV 批量导入批次。

设计建议：

- 上传文件后先进行格式校验
- 返回导入成功条数、失败条数、错误明细

#### GET /api/batches/export

用途：导出批次数据。

返回类型：

- `application/octet-stream`
- 或 `text/csv`

#### 批次/订单接口现状说明

- 前端已有订单页和来料页
- 真实数据库当前只有 `batchinfo`，没有订单主表
- 因此订单接口属于第二阶段扩展设计

## 5. 核心业务流程

### 5.1 来料入厂流程

1. 录入来料批次信息。
2. 校验批次编号唯一性。
3. 保存批次规格、重量、门幅、供应商等信息。
4. 将批次流入待排产或待检队列。

### 5.2 工艺建模流程

1. 建立工艺路线。
2. 维护工序标准信息。
3. 配置路线与工序关联顺序。
4. 建立工序与设备能力匹配关系。
5. 配置质检项目和摄像设备。

### 5.3 排产流程

1. 选择批次。
2. 选择工艺路线。
3. 生成生产计划主单。
4. 按路线拆分工序计划。
5. 结合设备能力分配机台。
6. 设置计划开始结束时间。
7. 在主计划页和甘特图中展示。

### 5.4 工序执行流程

1. 计划下发到工序。
2. 执行过程中录入工艺参数。
3. 设备侧或人员侧反馈执行状态。
4. 执行完成后进入质检或下一工序。

### 5.5 质检与异常处理流程

1. 根据 `planstep` 发起质检。
2. 记录 `qcrecord`。
3. 如有图像、视频或附件，记录到 `inspectiondata`。
4. 若判定异常，则生成 `exceptionrecord`。
5. 处理异常并记录关闭结果。
