## 1. 项目概述

### 1.1 系统背景

胚布排产质检系统面向纺织生产场景，核心诉求是将来料、工艺、设备、排产、过程参数、质检和异常处理纳入同一套业务平台中。系统既服务生产管理人员的计划编排与资源调度，也服务质检人员对过程质量、图像采集和异常追踪的管理需求。

从当前项目现状看，本系统不是单一的基础信息录入平台，而是一套围绕生产过程展开的数据闭环系统，主线包括：

- 来料批次登记与跟踪
- 工艺路线与工序标准配置
- 设备能力与工序匹配约束
- 生产计划拆分与工序级排产
- 工序过程参数记录
- 质量检验与图像采集
- 异常处理与闭环追踪
- 看板展示与追溯分析

### 1.2 系统目标

系统目标分为业务目标与技术目标两类。

业务目标：

- 实现来料批次基础数据标准化。
- 建立工艺路线、工序、设备能力之间的统一关系模型。
- 支持生产计划自动或半自动拆分到工序级。
- 支持工序过程参数、人工质检结果和视频质检结果统一沉淀。
- 支持异常从发现、记录到处理、关闭的全过程闭环。
- 为批次、工序、质检和异常提供可追溯的数据基础。

技术目标：

- 建立统一清晰的数据库与接口规范。
- 形成可扩展的前后端分层结构。
- 降低数据库命名、接口命名和页面命名之间的偏差。
- 为后续扩展订单、客户、报表、AI 辅助排产等模块预留设计空间。

### 1.3 技术架构

当前项目采用前后端分离架构：

- 前端：`Vue + TypeScript + Vite + Ant Design Vue + Pinia + Axios`
- 后端：`Spring Boot + MyBatis-Plus + MySQL`
- 数据库：`zhihuitong`
- 本地代理：`/prod-api -> http://localhost:8080`

当前阶段的系统实现状态如下：

- 前端模块已具备较完整的目录和页面结构，覆盖来料、工艺、排产、执行、质检、追溯和系统管理。
- 前端接口调用已经统一经过请求封装层处理，并使用统一响应结构。
- 后端目前主要是基础脚手架，具备统一返回、异常处理、健康检查和登录占位逻辑。
- 因此本开发文档中的接口设计属于“正式目标设计”，不代表当前后端已全部落地。

## 2. 数据库设计

### 2.1 数据库概览

真实数据库名称为 `zhihuitong`。经对真实数据库文件元数据核验，当前核心业务表共 14 张，覆盖排产质检主链路。

真实数据库的关键命名特征如下：

- 表名全部为小写且不带下划线，如 `batchinfo`、`processroute`、`productionplan`
- 字段名保留 camelCase，如 `batchId`、`routeId`、`planStepId`
- 当前 MySQL 实例启用了 `lower_case_table_names=1`

因此，后续开发中应统一遵守以下原则：

- 数据库表名以真实表名为准
- 文档中可使用逻辑名加括号标注真实表名
- 后端实体名可以保持 Java 风格，但映射必须指向真实表名

### 2.3 数据库关系链概览

- 主链路：`batchinfo -> productionplan -> planstep -> { processparameter, qcrecord, exceptionrecord }`
- 工艺链：`processroute -> routestep -> processstep`
- 设备链：`processstep <-> stepmachinecapability <-> machine`
- 质量链：`qcitem -> qcrecord`，`qccamera -> inspectiondata`，`qcrecord -> inspectiondata`

结构特点：

- `planstep` 是计划、执行、质检、异常的共同连接点
- 质检与视频识别结果可通过 `qcrecord + inspectiondata` 联合表达
- 当前数据库只覆盖排产质检核心域，不覆盖订单、客户、报工、权限等外围域

## 4. 接口设计

字段级详细设计可继续参考：[接口详细设计.md](C:/Users/lhr/Desktop/saas/frontend/docs/接口详细设计.md)

接口设计原则：

- 统一采用 REST 风格 `/api/**`
- 资源命名统一使用复数名词，并优先采用中划线风格，如 `/api/batches`、`/api/process-routes`、`/api/production-plans`
- 资源标识统一通过路径参数传递，如 `/api/batches/{batchId}`
- 列表查询统一使用 `GET`，查询条件通过 query string 传递
- 分页参数统一：`pageNum`、`pageSize`
- 列表接口统一返回：`{ code, msg, rows, total }`
- 明细接口统一返回：`{ code, msg, data }`
- 写操作统一返回：`{ code, msg, data }`
- 创建使用 `POST`，全量更新使用 `PUT`
- 状态流转或局部更新使用 `PATCH` 或语义化子资源接口
- 删除默认采用逻辑删除语义；若执行物理删除，必须增加引用校验
- 状态值、类型值、判定值统一采用英文编码，前端通过字典映射显示中文
- 时间字段统一格式：`yyyy-MM-dd HH:mm:ss`
- 导入、导出、批量关闭等能力统一设计为独立动作接口

统一响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

列表响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "rows": [],
  "total": 0
}
```

### 4.1 批次/订单接口

#### 批次接口

`GET /api/batches`

用途：批次列表查询。

请求参数：

- `pageNum`
- `pageSize`
- `batchNo`
- `supplier`
- `dateFrom`
- `dateTo`

返回字段建议：

- `batchId`
- `batchNo`
- `supplier`
- `inDate`
- `weight`
- `width`
- `composition`
- `status`

`GET /api/batches/{batchId}`

用途：查询批次详情。

返回建议：

- 批次基础信息
- 关联生产计划摘要
- 关联质检记录摘要
- 异常记录数量

`POST /api/batches`

用途：新增批次。

请求体示例：

```json
{
  "batchNo": "BAT-20260522-001",
  "supplier": "华东供应商A",
  "inDate": "2026-05-22 08:30:00",
  "weight": 2500.50,
  "width": 168.00,
  "composition": "棉 95%, 氨纶 5%",
  "note": "首批试产"
}
```

`PUT /api/batches/{batchId}`

用途：修改批次信息。

`DELETE /api/batches/{batchId}`

用途：作废批次或执行删除。

设计说明：

- 正式设计建议优先逻辑作废
- 已被计划引用的批次不得物理删除

`POST /api/batches/import`

用途：批量导入批次。

`GET /api/batches/export`

用途：导出批次数据。

#### 订单接口

订单模块当前不在核心数据库 14 张表内，但为满足目录设计完整性，接口规范建议先预留：

- `POST /api/orders`
- `PUT /api/orders/{orderId}`
- `PATCH /api/orders/{orderId}/status`

现状说明：

- 当前前端已有订单页雏形

## 5. 核心业务流程

### 5.1 来料入厂流程

1. 录入来料批次基础信息。
2. 校验批次编号唯一性。
3. 保存批次规格、重量、门幅、成分、供应商等信息。
4. 根据业务规则将批次置为待排产、待检或待确认状态。

### 5.2 工艺建模流程

1. 创建工艺路线。
2. 维护标准工序信息。
3. 配置路线和工序的顺序关系。
4. 维护工序与设备能力关系。
5. 维护质检项目标准与摄像设备基础信息。

### 5.3 排产流程

1. 选择待排产批次。
2. 选择适用工艺路线。
3. 创建生产计划主单。
4. 根据路线拆分生成工序计划。
5. 根据设备能力确定可执行设备。
6. 设置开始结束时间与工序顺序。
7. 在主计划页和甘特图中展示结果。

### 5.4 工序执行流程

1. 工序计划下发。
2. 执行过程中采集或录入工艺参数。
3. 更新工序执行状态。
4. 执行完成后进入下一工序或进入质检流程。

### 5.5 质检与异常处理流程

1. 根据 `planstep` 发起质检。
2. 记录 `qcrecord` 主数据。
3. 若存在图像、视频或附件，则写入 `inspectiondata`。
4. 若判定异常，则生成 `exceptionrecord`。
5. 异常处理完成后记录处理结果并关闭。
