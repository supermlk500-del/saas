## 1. 项目概述

### 1.1 系统背景

胚布排产质检系统面向纺织生产场景，核心诉求是将订单、来料、工艺、设备、排产、过程参数、质检和异常处理纳入同一套业务平台中。系统既服务业务侧对订单交付、客户需求、交期和优先级的管理，也服务生产管理人员的计划编排与资源调度，并进一步支撑质检人员对过程质量、图像采集和异常追踪的管理需求。

按订单驱动改造后的目标形态看，本系统不是单一的基础信息录入平台，而是一套围绕生产过程展开的数据闭环系统，主线包括：

- 订单录入与订单明细管理
- 订单与来料批次的关联分配
- 来料批次登记与跟踪
- 工艺路线与工序标准配置
- 设备能力与工序匹配约束
- 基于订单需求生成生产计划并拆分到工序级
- 工序过程参数记录
- 质量检验与图像采集
- 异常处理与闭环追踪
- 看板展示与订单级追溯分析

### 1.2 系统目标

系统目标分为业务目标与技术目标两类。

业务目标：

- 实现订单主数据、订单明细与来料批次数据标准化。
- 建立“订单 -> 订单明细 -> 批次 -> 计划 -> 工序”的统一业务关系模型。
- 建立工艺路线、工序、设备能力之间的统一关系模型。
- 支持以订单为主入口自动或半自动拆分生产计划到工序级。
- 支持工序过程参数、图片离线质检结果和实时视频流质检结果统一沉淀。
- 支持异常从发现、记录到处理、关闭的全过程闭环。
- 为订单、批次、工序、质检和异常提供可追溯的数据基础。

技术目标：

- 建立统一清晰的数据库与接口规范。
- 形成可扩展的前后端分层结构。
- 降低数据库命名、接口命名和页面命名之间的偏差。
- 为后续扩展客户、报表、交期优化、AI 辅助排产等模块预留设计空间。

### 1.3 技术架构

当前项目采用前后端分离架构：

- 前端：`Vue + TypeScript + Vite + Ant Design Vue + Pinia + Axios`
- 主后端：`Spring Boot + MyBatis-Plus + MySQL`
- 质检推理模块：`Java + ONNX Runtime + YOLO ONNX模型`
- 数据库：`zhihuitong`
- 本地代理：`/prod-api -> http://localhost:8080`

当前架构决策补充如下：

- 排产算法继续保留在 Java 主后端实现，并与 `orderinfo`、`orderitem`、`orderbatchlink`、`productionplan`、`planstep` 等主业务表协同
- 订单成为排产主驱动对象，批次继续作为执行层资源对象存在
- 质检算法不再采用独立 Python 服务，而是由 Java 主后端内部集成 ONNX Runtime 完成图片/视频帧推理
- 前端仍然只调用 Java 主后端，不感知检测实现从远程服务切换为本地推理
- Java 主后端负责接收上传图片、执行 ONNX 推理、写入 `qcrecord`、`inspectiondata`，同时继续承担异常闭环逻辑

当前阶段的系统实现状态如下：

- 前端模块已具备较完整的目录和页面结构，覆盖来料、工艺、排产、执行、质检、追溯和系统管理。
- 前端接口调用已经统一经过请求封装层处理，并使用统一响应结构。
- Java 后端已完成批次、工艺、排产、质检、异常等核心业务骨架，并具备一版规则式排产逻辑。
- Java 后端已落地订单模块、订单排产池、订单详情聚合、批次资源池等订单驱动能力。
- 质检检测链路已由 Java 内部 ONNX Runtime 承担，前端已联动离线检测、实时流检测与快照落库。
- 当前 ONNX 模型文件位置为：`C:\Users\lhr\Desktop\saas\docs\best.onnx`
- 因此本开发文档中的接口设计应优先以当前代码实现与增量脚本口径为准，而不是仅作为目标态描述。

## 2. 数据库设计

### 2.1 数据库概览

真实数据库名称为 `zhihuitong`。经对真实数据库文件元数据核验，当前基线 SQL 共 14 张核心表，覆盖排产质检主链路；当前代码依赖的订单域结构和 `productionplan` 扩展字段定义在 `docs/order_schema_upgrade.sql` 中。

真实数据库的关键命名特征如下：

- 表名全部为小写且不带下划线，如 `batchinfo`、`processroute`、`productionplan`
- 字段名保留 camelCase，如 `batchId`、`routeId`、`planStepId`
- 当前 MySQL 实例启用了 `lower_case_table_names=1`

因此，后续开发中应统一遵守以下原则：

- 数据库表名以真实表名为准
- 文档中可使用逻辑名加括号标注真实表名
- 后端实体名可以保持 Java 风格，但映射必须指向真实表名

### 2.3 数据库关系链概览

- 订单驱动主链路：`orderinfo -> orderitem -> orderbatchlink -> batchinfo -> productionplan -> planstep -> { processparameter, qcrecord, exceptionrecord }`
- 工艺链：`processroute -> routestep -> processstep`
- 设备链：`processstep <-> stepmachinecapability <-> machine`
- 质量链：`qcitem -> qcrecord`，`qccamera -> inspectiondata`，`qcrecord -> inspectiondata`

结构特点：

- `orderitem` 是排产业务需求的直接来源
- `orderbatchlink` 是订单需求和批次资源之间的桥接层
- `planstep` 是计划、执行、质检、异常的共同连接点
- 质检与视频识别结果可通过 `qcrecord + inspectiondata` 联合表达
- 当前真实数据库只覆盖排产质检核心域，订单驱动改造需补充订单域表结构

### 3.6 质量管理模块

功能范围：

- 质检结果录入

- 实时视频流质检
- 质检结论判定
- 异常生成与闭环处理

核心数据表：

- `qcitem`
- `qcrecord`
- `qccamera`
- `inspectiondata`
- `exceptionrecord`

设计重点：

- 将“图片离线质检”和“实时视频流质检”作为两条独立业务模式设计
- 图片离线质检：由用户上传单张图片或样本图，触发一次性检测
- 实时视频流质检：由前端调用电脑摄像头采集实时视频流，并与后端建立持续检测会话，由后端对连续视频帧执行近实时 ONNX 推理
- 质检主记录与附件证据分离存储
- 质检异常可直接进入异常闭环流程
- 质检检测能力统一收敛到 Java 主后端内部，通过 ONNX Runtime 本地推理完成结果生成与落库
- 原始上传图片统一存储到 `C:\Users\lhr\Desktop\saas\photo\upload`
- 算法结果图统一存储到 `C:\Users\lhr\Desktop\saas\photo\results`
- 当前阶段默认接入“电脑摄像头”，后续再扩展工业摄像头、网络摄像头等更多视频源
- 实时视频流检测不应退化为“先截图再检测”的单帧图片模式
- 为保证实时性，视频流检测结果应优先做内存级返回，只有关键帧、异常帧或人工确认帧才写入 `inspectiondata`

## 4. 接口设计

字段级详细设计可继续参考：[接口详细设计.md](C:/Users/lhr/Desktop/saas/docs/接口详细设计.md)

接口设计原则：

- 统一采用 REST 风格 `/api/**`
- 资源命名统一使用复数名词，并优先采用中划线风格，如 `/api/batches`、`/api/process-routes`、`/api/production-plans`
- 资源标识统一通过路径参数传递，如 `/api/batches/{batchId}`
- 列表查询统一使用 `GET`，查询条件通过 query string 传递
- 分页参数统一：`pageNum`、`pageSize`
- 列表接口统一返回：`{ code, msg, rows, total }`
- 明细接口统一返回：`{ code, msg, data }`
- 写操作统一返回：`{ code, msg, data }`
- 创建使用 `POST`，全量更新使用 `PUT`
- 状态流转或局部更新使用 `PATCH` 或语义化子资源接口
- 删除默认采用逻辑删除语义；若执行物理删除，必须增加引用校验
- 状态值、类型值、判定值统一采用英文编码，前端通过字典映射显示中文
- 时间字段统一格式：`yyyy-MM-dd HH:mm:ss`
- 导入、导出、批量关闭等能力统一设计为独立动作接口

统一响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {}
}
```

列表响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "rows": [],
  "total": 0
}
```

## 5. 核心业务流程

### 5.1 来料入厂流程

1. 录入来料批次基础信息。
2. 校验批次编号唯一性。
3. 保存批次规格、重量、门幅、成分、供应商等信息。
4. 根据业务规则将批次置为待排产、待检或待确认状态。

### 5.2 工艺建模流程

1. 创建工艺路线。
2. 维护标准工序信息。
3. 配置路线和工序的顺序关系。
4. 维护工序与设备能力关系。
5. 维护质检项目标准与摄像设备基础信息。

### 5.3 排产流程

1. 录入订单主信息和订单明细。
2. 为订单明细分配可用来料批次。
3. 选择适用工艺路线。
4. 创建生产计划主单。
5. 根据路线拆分生成工序计划。
6. 根据设备能力确定可执行设备。
7. 设置开始结束时间与工序顺序。
8. 在主计划页和甘特图中展示结果。

### 5.4 工序执行流程

1. 工序计划下发。
2. 执行过程中采集或录入工艺参数。
3. 更新工序执行状态。
4. 执行完成后进入下一工序或进入质检流程。

### 5.5 质检与异常处理流程

1. 根据 `planstep` 发起质检。
2. 若为图片离线质检，则上传图片并触发一次性检测。
3. 若为实时视频流质检，则前端调用电脑摄像头采集视频流，并与后端建立持续检测会话。
4. 记录 `qcrecord` 主数据。
5. 若存在原图、结果图、视频帧或附件，则写入 `inspectiondata`。
6. 若判定异常，则生成 `exceptionrecord`。
7. 异常处理完成后记录处理结果并关闭。

- `com.zhihuitong.modules.trace`
- `com.zhihuitong.modules.exception`

接口风格统一建议：

- 统一使用 `/api/**`
- 不再以旧前端 `/business/**` 路径为兼容目标
- 优先保证资源建模清晰、命名一致、语义稳定
- 统一分页参数与统一返回结构
- 状态值统一使用字典编码，不在前端写死中文字符串

开发实现补充建议：

- Java 实体名可保留 `BatchInfo`、`ProductionPlan` 等写法
- 数据库映射必须严格指向真实表名 `batchinfo`、`productionplan`
- DTO 与 VO 应围绕接口视图设计，而不是直接暴露数据库实体
- 排产算法继续在 `com.zhihuitong.modules.plan` 下演进，不另建 Python 排产服务
- 质检检测建议在 Java 中新增 `com.zhihuitong.modules.ai` 模块，统一封装 ONNX 模型推理能力
- 质检业务集成建议继续放在 `com.zhihuitong.modules.quality` 下，并通过 service 调用 `modules.ai`

## 9. 测试与验证建议

- 单元测试：覆盖 Service 层核心逻辑，如计划生成、状态变更、异常关闭
- 接口测试：覆盖增删改查、分页、必填项校验、外键引用校验
- 集成测试：验证订单到批次、批次到计划、计划到工序、工序到质检、质检到异常的完整链路
- 数据完整性校验：重点验证主键、唯一键、外键关系
- 前后端联调测试：验证列表和明细响应结构是否一致
- 异常测试：验证非法状态流转、重复编号、缺失关联数据等场景

## 10. 后续迭代规划

- 扩展订单、客户、产品等外围业务表
- 补充报表中心与统计分析能力
- 持续增强 Java 排产算法能力，如多约束排产、优先级排产、重排优化
- 引入并优化 Java 内部 ONNX 智能质检能力，完成与现有质检业务链路的稳定集成
- 完善权限管理、操作日志、流程审计模块
- 补充质检任务、模板、NCR、CAPA 等独立实体
- 重绘与真实数据库一致的 E-R 图和接口时序图

结论：

当前项目最稳妥的推进方式，是以真实数据库 14 张核心表为第一阶段落地点，优先打通“批次 -> 计划 -> 工序 -> 质检 -> 异常”的主链路；在实现策略上，排产算法继续留在 Java 主后端，质检检测改为 Java 内部 ONNX Runtime 本地推理，订单、执行、追溯和高级质量模块作为第二阶段扩展域逐步补齐。
